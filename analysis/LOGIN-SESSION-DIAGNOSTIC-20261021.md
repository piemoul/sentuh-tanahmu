# Login and preview session diagnostic

The current implementation has a reproducible cross-tab synchronization gap. Login and logout rotate the same-origin browser cookie and CSRF, while another already open tab retains its previous authenticated flag and CSRF in memory. Its next POST fails with `CSRF_REJECTED` before any provider request. A local `GET /api/state` recovers the active session without credentials or another provider sign-in. This is a verified mechanism, **not proof that it caused the user's reported login mismatch**.

No runtime source was edited. No actual credentials, cookies, tokens, account identifiers or browser storage were read. No official login, account request, map request, GPS request or mutation was made. The two transport sign-ins in the new diagnostic use explicit synthetic credentials and an injected local response.

- Zero upstream sign-in records does **not** establish that no local login form was submitted: host/origin/CSRF rejection happens before transport, and this implementation does not log those local rejections.
- The retained `webapp/swaplotting-live-account-check-20261021.json` records an anonymous primary preview both before and after deliberate document reload, with no backend recreation during that check. Therefore the later replacement does not, by itself, explain that earlier mismatch. The artifact's date has no precise time, so do not infer a stronger chronology.
- A successful login on localhost, 127.0.0.1, or the public HTTPS domain does not imply a login at another origin. The backend deliberately binds sessions to the exact request origin. Whether the user actually crossed origins, tabs, browser profiles, or a storage partition was not established.

## Recommended next action

First inspect the primary preview's current DOM, then use a local state refresh before assuming another provider login is necessary. If that refresh reveals authentication, immediately perform the pending read-only Perjalanan Berkas check before any backend replacement.

A bounded frontend improvement can resynchronize local session state on an explicit account refresh or a guarded return to the active tab. Typed local CSRF failures can offer that same local refresh. **Do not automatically replay the failed login, upload, or other POST.** Any automatic state refresh must retain existing authentication/load epochs, suppress stale responses, and avoid disrupting an in-flight or accepted submission or its owned dialog. Logout/account changes must continue to clear private data. No security relaxation, persistent credentials, periodic provider login, or longer expiry is needed to address this synchronization gap.

If the primary preview remains anonymous after a successful local state bootstrap, the evidence is still insufficient to identify the user's actual login path. Ask for neither credentials nor a repeated login claim as a substitute for observable state. Preserve the unresolved account E2E gate in the progress report.
