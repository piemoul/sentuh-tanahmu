# Profile destination follow-up

This is a bounded offline audit of four native profile callbacks. It reads the pinned ARM64 ELF and pool; it does not launch the APK, request pages, use a session, or change application code. Contact is a separate sibling audit in `analysis/recovered/profile-contact-followup`; its subtree is intentionally outside this ledger.

The canonical ledger is [flow.json](recovered/profile-destinations-followup/flow.json), SHA-256 `a96bd73805664e097f3611567f322f521664009e743c144578ce311db4cd82da`. Independent verification is [verify_profile_destinations_followup.py](rea/verify_profile_destinations_followup.py), with [verification.json](recovered/profile-destinations-followup/verification.json). The verifier checks 10 source windows / 618 ELF instructions, 42 calculated pool bindings, 52 decisive markers, four class records and six dependency hashes. All prior evidence remains untouched.

For all three web destinations, callback navigation goes through `OPh` and shared helper `6ba6fc`. The destination allocator `d8c384` has class ID 6138 (`DRb`); title, URL and false flag are written at tagged-pointer offsets `0xb`, `0xf`, `0x13` (class field offsets `0xc`, `0x10`, `0x14`). Builders concatenate the base and suffix directly, with no slash insertion or URL normalization in these windows. They contain neither copied page content nor an API operation. The shared navigator and destination rendering internals are outside this proof; the `DRb` name alone is not a complete audit of WebView lifecycle or browser embedding policy.

The public-site base must not be inferred from the unrelated Help constant `https://bantuan.atrbpn.go.id/sentuhtanahku/`. Its field-table slot is loaded without a sentinel check here. Existing metadata does not expose the corresponding field object. A targeted binary instruction-index search found no direct 64-bit or 32-bit immediate store at offset `0x2fd8`, nor the narrowly checked page-add `0x2000` plus store `0xfd8` form. This negative search does **not** prove there is no initializer, indirect assignment, or startup configuration. The ledger keeps its value `null` and `base_origin_bound:false`.

The rating action passes the constructed URI through `d2a3a8`, which contains plugin method literal `canLaunch` and a `url` argument. The success branch invokes `d2a0fc`; that wrapper includes the explicit requirement for an HTTP(S) URL when using an in-app webview mode. A false `canLaunch` logs `Could not launch `; the action's catch logs `Error opening app store: `. This closure does not submit a star value or a written review. Its entry also uses shared event/instrumentation helper `6bd5d0` with label `klik menu beri kami nilai`; this audit does not certify that helper has no network effects.

The complete public production URL `https://play.google.com/store/apps/details?id=id.go.bpn.sentuh` is independently present at pool offset `0x240d0`. Nearby code `93c384..93c458` is a package initializer candidate: a true `TRb.Thj` path yields `id.go.bpn.sentuh`, while the other path appends `.dev` to `Wxb.zYi`. Existing initializer metadata binds `TRb.Thj` to `ca53e0`, whose two instructions return native true. The candidate's own `TRb.zYi → initializer` metadata binding is absent, so the ledger expressly distinguishes this candidate from a completed field initializer proof. A browser link to the independently bundled production store URL is a documented browser adaptation, not a claim that every runtime flavor resolves that exact URL.

Implementation can preserve these profile labels and titles now. It should keep the three site URLs unavailable until the shared base is independently bound or the destination is explicitly configured with a clear provenance label. It must not silently replace their distinct destinations with generic Help/FAQ content. Isolated explicit hyperlinks are reasonable browser adaptations for proven public destinations; they must not carry private session headers, tokens, client keys or account data.

No remote page response, current page content, native device behavior, application completeness, or production mutation is established here. Account-verification work, inline Berkas mapping, and all physical-location/attestation requirements remain separate scopes. This audit provides no spoofing, visit, activation, geotag, or credential bypass.
